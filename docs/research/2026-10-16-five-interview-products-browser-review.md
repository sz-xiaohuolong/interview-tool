# 五款面试产品浏览器实查与下一轮功能建议

- 调研日期：2026-10-16。
- 本次补充：用户完成内置浏览器登录后，实查四站登录后页面；快面完成一场合成文字模拟及报告，牛客完成合成项目改写、事实纠正与押题。
- 对照基线：本仓库提交 `e922153` 及调研时工作区；本次没有改动业务代码。
- 文档性质：研究结论、候选功能和后续文档编写提示词，不构成新版本需求批准。
- 当前状态：正式 Release 仍为 V1；五项 V2 功能已实现并在本机启用，整体验证为 PARTIAL，等待人工验收。
- 与旧报告的关系：[2026-10-15 调研](2026-10-15-interview-platforms.md)保留当时 V1 的判断；本报告补充五款指定产品的真实浏览器观察，并更新“我们还缺什么”的判断。

## 1. 结论

我们已经具备“简历 / 项目输入 → 动态追问 → 逐题复盘 → 复习与重答”的主要流程。登录实查后，建议继续优先解决项目证据与训练范围，再做保真改写和口述训练。快面的实际追问证明回答驱动的追问有用，但这项我们已经具备；值得新增的是让用户清楚看见依据、缺口，以及下一步练什么。

以下顺序是针对本项目定位的判断，不是竞品市场份额或实测效果排名。

| 建议顺序 | 功能 | 与当前能力的准确差别 | 首次交付的用户结果 |
|---|---|---|---|
| 1 | 项目深挖覆盖与证据缺口 | 深化已有 L1/L2/L3 和动态追问 | 知道项目哪些地方没有讲清、哪些说法缺依据，并直接练对应问题 |
| 2 | 技术专题题库与自选题单 | 新增可浏览、可选择、可保存的出题范围 | 选择 Java 并发、Redis、RAG 或 Agent 工具调用等专题，按题单练习 |
| 3 | 简历逐条诊断与保真改写 | 深化已有押题、风险提示、JD 诊断和故事版本 | 看见原句、问题和修改建议，逐条确认，形成可追溯版本 |
| 4 | 语音口述、转写确认与回放 | 新增音频输入和口头表现证据 | 能说出回答、检查转写、回听原话，再结合现有点评重答 |
| 5 | 计时与完整面试轮次 | 新增实际时间约束和阶段安排 | 在明确时限下完成开场、技术、项目和反问，并看到各阶段表现 |

如果只做两项，优先选择前两项。本次把保真改写由第 4 调到第 3：牛客在合成样本中补入了未提供的职责与处理成果，用户纠正后才收窄，说明事实确认是核心问题。语音仍有价值，但本次没有录音质量证据，且需增加音频与转写依赖，先做受控验证再扩展。

还有三项应融入这五项的共通设计：启动前明确本场资料与版本；把准备、押题、练习和复盘串起来；报告区分未作答、答错和证据不足。当前已能选择项目或简历并保存上下文，不能把“资料选择”再包装成全新能力，也不因竞品出现知识库按钮就优先建设大型检索系统。

## 2. 真实浏览器使用范围

### 2.1 使用了什么，实际做到哪里

前期成功复用了用户现有 Chrome 的 CDP 会话，读取五款产品的可访问页面；随后按用户要求切换至 Codex 内置浏览器。前期内置浏览器尚未登录，只能访问公开页面；本次用户自行完成登录后，继续复用同一内置浏览器会话，面多多、牛面、快面和牛客均实际进入了登录后页面。Yoodli 仍停留在登录页。

本次使用的是用户在内置浏览器建立的各站点登录态，没有复制工作 Chrome 的 Cookie，也没有导出凭证。Google 登录不等于自动获得各面试网站的登录态。

| 产品 | 登录状态 | 本次实际验证深度 | 仍未验证的边界 |
|---|---|---|---|
| 面多多 | 已登录 | 综合向导走到第 4 步，填写合成个人描述；查看时长和创建前配置预览 | 能量为 0，未创建正式面试；追问、数字人和报告未测 |
| 牛面 | 已登录 | 个人中心额度、简历优化表单和 Java 专项配置 | 可用训练额度为 0，优化表单提示不足；未提交任务或启动面试 |
| 牛客 | 已登录 | Java 面试封面与项目陪练；实际提交合成项目，完成改写、事实纠正及三题押题 | 未进入视频模拟，未授予设备权限，未取得语音或视频报告 |
| 快面 | 已登录 | 创建独立合成简历和岗位；完成 4 次文字回答、一次真实追问、提前结束、报告、逐题展开及文字回放 | 未录音、未开摄像头、未验证 30 分钟 / 12 题上限和知识库检索效果 |
| Yoodli | 未登录 | 官网与登录入口 | 未见登录后训练与个人报告 |

用户明确授权用合成资料使用快面的 1 次模拟额度。实际只启动并结束 1 场，未重新生成报告或再开一场。配置页在开始前和结束后都显示剩余 1 次，**因此无法确认实际扣减，不能写成“已扣减 1 次”或“确认免费”**。

本次在快面留下独立的合成简历、合成岗位和一条模拟历史，在牛客留下合成项目陪练会话。原有简历未修改，未把真实简历或私人 JD 绑定到新面试；没有充值、购买、新建账号、上传个人文件或录音，也没有授予麦克风或摄像头权限。没有修改 Chrome 的调试保护，切换后未再连接工作 Chrome。

这些证据支持比较实际流程，并对快面报告和牛客改写提出样本范围内的观察；只有一份合成项目与一场短模拟，不能据此排名产品整体准确率或训练效果。

### 2.2 如何理解证据

| 类型 | 含义 | 不能推出什么 |
|---|---|---|
| 页面实见 | 实际浏览器中看见入口、字段、分类、向导或登录限制 | 看见按钮不代表完整业务已验证 |
| 合成实测 | 提交明确标识的合成资料，实际取得问题、改写或报告 | 单次输出不能代表全部用户、模型稳定性或实际求职效果 |
| 官网说明 | 在产品官网读到功能描述或展示图 | 不是实际完成一场训练的证据 |
| 本仓库事实 | 核对当前源码、提示词和版本文档 | 已有实现不等于所有真实输入质量均通过 |
| 设计建议 | 根据差距提出的本项目实现方式 | 不是对竞品后台架构、算法或供应商的逆向确认 |
| 未知 | 登录、额度、未执行流程或服务端不可见部分 | 不补写为“支持”，也不判定为“不支持” |

REA 浏览器目标发现和被动页面观察均返回超时，原始错误保留在本机证据目录。没有把它们记作成功分析。本报告的运行时依据来自成功的 Chrome CDP 页面观察及内置浏览器交互；没有取得竞品服务端实现、模型提示词、语音供应商或追问算法。此前报告中的公开脚本静态分析仍只适用于其记录的产品与产物。

### 3.1 快面：一场合成模拟的实际结果

**样本与操作**：独立创建合成简历与初级 Java / Agent 岗位，核对选中状态后开始；未选择知识库，使用键盘作答。项目是本地教学用文档问答练习，只有接口、文档切分、向量检索与人工核对，没有生产用户、性能成绩或部署经历。新建简历在本次生成中保留了这些主要边界，没有看到原真实简历内容混入。[B08、B14]

| 验证点 | 输入或操作 | 实际输出 | 可用于我们的判断 |
|---|---|---|---|
| 回答驱动追问 | 首答只说人工核对，未说明方法 | 追问如何判断回答是否受资料支持，要求举例 | 本次追问确实针对上一答；我们已有该能力，应加强追问证据与覆盖展示 |
| 故意错误 | 用关键词重合作为依据，给出不被片段支持的一致性结论 | 下一轮指出关键词不能证明结论受支持，然后转向接口实现；报告也定位该错误 | 一次错误被识别，不代表所有技术事实都能判断；可复用为我们后续的固定质量样本 |
| 实现与设想 | 明说空检索仍调用模型；校验、拒答和版本引用只是计划 | 问答反馈认可边界区分，报告仍把未落地的防护列为不足 | 报告应分别记录事实、设计能力与实践证据，不能混为同一个完成状态 |
| 提前结束 | 提交 4 次回答，其中一次为追问回答；下一道主问题已发出但未答时结束 | 生成总分 58、五维评分、优缺点、详细评估、四组主问题回顾及后续建议；未答主问题记为 0 分 | 训练报告应单列未作答与提前结束原因；若实战规则计分，需事前说明，不能默认解释成不会 |
| 可追溯性 | 展开首题并打开回放 | 首题回顾合并主答与追答；文字回放保留问题、追问标记和回答 | 我们应保留消息级定位，让覆盖缺口、点评和补练能回到具体回答 |

实际报告中的后续建议落到了依据核对、拒答与引用、接口异常、结构化输出和切分评测等主题，比笼统的“加强基础”更可操作。但本次没有验证建议能否一键生成新的训练或持续追踪，也没有重新生成报告检查稳定性。58 分只是该合成短场的输出，不能当客观能力标尺或产品质量分。[B08]

计时在页面实际增长，回放将本场显示为约 2 分钟；这只能证明显示和归档，未证明刷新恢复、模型等待扣时和到时强制结束。回放显示的轮次数与人工统计的回答次数口径也不同，本报告以实际 4 次提交为准，不把界面轮数直接写成主问题数。

### 3.2 牛客：连续准备流程与改写的事实风险

项目陪练先询问求职岗位，再确认是否补充 JD，之后输出项目介绍；纠正后给出三道项目问题及回答思路。这条“整理资料 → 明确岗位 → 改写 → 押题 → 模拟”的连续流程值得借鉴，我们可以复用已有 JD、故事、押题、练习和复习，把同一资料版本贯穿起来。[B13]

本次初稿把只提供了部分职责的项目扩写成独立完成，并加入已处理无依据回答、保障准确性的成果；这些事实没有在输入中成立。提交具体纠正后，后续文本删除了上述主要断言，收窄为接口、检索和人工核对，并把未完成项单列。因此，不能把“模型承诺不编造”当成事实校验，也不能只核对数字；职责范围、完成程度、质量保证同样需要依据。此判断只针对本次合成样本，不据此评定牛客整体质量。

押题与回答思路在进入模拟前已经展示。我们若把该流程接入同题对照，必须保留答案已暴露的状态，避免把看过提示后的表现直接解释为独立能力进步。未进入视频环节，不声称完成其完整陪练与报告。

### 3.3 从可见行为推导实现方式

以下是本项目的实现建议，不是对竞品服务器的逆向确认。REA 本次超时；没有接口抓包证据，不能推断具体模型、向量库、检索参数或评分公式。

| 已观察到的行为 | 我们可以怎样实现 | 需要先验证什么 |
|---|---|---|
| 快面可临时改变本场参考资料；界面说明检索片段并仅影响本场 | 先在现有资料选择上显示本场清单，保存资料版本与来源；真正需要多资料时再扩展作用域；长文检索另行评估 | 不选择的资料不会进入上下文；资料更新不改变旧场；不能用界面文案证明检索质量 |
| 面多多创建前预览配置 | 汇总岗位、资料版本、题单或检查点、时间规则和已看提示状态，确认后固定快照 | 预览与实际启动一致，修改后重新确认；无需为预览新增一套会话数据 |
| 牛客把准备和练习连续组织 | 让同一项目或简历版本关联现有 JD、故事、押题、单题练习与复习；用户决定何时进入下一步 | 更换资料或 JD 后旧结果仍可识别；准备提示暴露不丢失 |
| 快面报告回到原问答并提出后续主题 | 项目检查点与具体消息关联，反馈必须给依据；把可补练项接入现有练习入口 | 未答、答错、缺资料、仅有设想分别展示；不重复建设复习队列 |
| 牛客改写可被用户纠正 | 每条建议带原文、事实依据、改写和待补项，逐条确认保存版本 | 防止把部分参与改成独立负责，把计划改成成果；旧版本和用户纠正保留 |

## 4. 对照当前实现：哪些不能再算新增功能

| 能力 | 我们当前已有的内容 | 还值得补的内容 |
|---|---|---|
| 简历押题 | 10 道准备题、资料依据、优先级、风险、回答结构、可能追问及单题练习 | 对原简历逐条提出建议、可确认改写和版本关联 |
| 项目深挖 | L1 整体理解、L2 技术实现、L3 假设挑战与取舍；根据真实回答追问 | 可见覆盖、事实证据缺口、定向补练及跨次回看 |
| 动态追问 | 每道主问题最多两次，由服务端限制 | 可解释的追问方向和覆盖策略；不是首次接入动态追问 |
| 复盘与长期训练 | 逐题报告、复习队列、能力档案、同题二答和对照 | 新题单、音频和项目覆盖结果接入现有流程 |
| 岗位准备 | JD 要求提取、证据诊断和 7 天参考清单 | 更方便地把诊断连接到专题、项目缺口和简历修改 |
| 自我介绍与行为素材 | 自我介绍 / STAR 故事、事实确认、版本和文本练习 | 真实口述、有时间限制的场景演练；谈薪等独立情景仍可后续评估 |
| 系统与 Agent 设计 | 两个合成案例、五阶段结构化产物和反馈 | 后续内容扩展；当前两个案例不等于开放技术题库 |
| 时间与媒体 | 5 / 10 / 20 分钟用于选择约 3 / 5 / 8 道主问题；页面明确“不限时”；文本输入 | 实际计时、阶段节奏、录音、转写和音频回放 |
| 本场资料 | 简历 / 项目选择、JD 输入、创建时的上下文保存与截断提示 | 资料版本和用途更清晰的确认；多资料范围可另行设计，不等于当前已支持任意知识库检索 |

仓库依据为 [R01～R09](#8-来源与复查入口)。本表采用 V2 已实现的现状，不能直接沿用旧报告以 V1 为基线的缺失项清单。

## 5. 五项功能的最小方案

以下都是待审核的本项目方案，不是已经实现的功能。复杂度只表示相对投入，不承诺工期。

五项都应复用同一组资料版本、问答消息和尝试记录。启动时确认本场所用资料和已暴露的提示，结果中区分“未作答、回答错误、资料不足、仅有改进设想”，让建议能回到原文和具体回答。它们是共通约束，不是额外增加五套资料管理或评分系统。

### 5.1 项目深挖覆盖与证据缺口

**为什么排第一**：最贴合“技术岗、简历押题、项目深挖”的重点，也最能复用当前的资料依据与追问能力。快面实测能识别问题，但复盘仍需分清未答和答错；牛客改写也暴露了职责依据不足的风险。本次未见它们完整的项目证据覆盖界面，这里的差异化判断来自本项目定位，不能宣称竞品没有该能力。

**最小流程**：选择项目 → 确认事实与训练检查点 → 开始深挖 → 复盘覆盖 → 针对缺口再练。

- 先维护少量检查点：业务目标、个人职责、架构与数据流、选型依据、异常处理、性能证据、替代方案。Java 与 Agent 可以有各自的少量扩展项。
- 每项关联项目原文和真实回答，区分“尚未问到”“已问未说明”“有回答依据”“说法待澄清”。这些状态不直接等于技术掌握程度。
- 回答证据表示候选人说过什么，不能等同于代码已经实现；资料记载、候选人自述和后续改进设想分别标明。提前结束导致未答的问题独立记录，不自动归为答错。
- 资料里写“高并发”，回答未提供负载和测量方法时，提示补充验证过程，不能直接认定指标虚假，也不能替用户生成 QPS。
- 复用已有单题练习与复习项。下一次训练可以选择一个未覆盖检查点；沿用现有追问上限，是否改变上限另行审核。
- 覆盖总结默认在复盘展示，避免面试中把答案检查表提前透露给用户。

**建议实现**：保存本场检查点版本、来源快照、对应问答和用户确认记录。服务端核对引用及合法状态；不能让模型凭一句“已覆盖”改变全部进度。先用列表与证据展开，不建设图数据库或全项目代码分析器。

**关键验收**：同一问答重复整理不重复计数；未问到不判错；资料更新后旧结论保留当时版本；用户可纠正错误归因；原问题与追问仍可回看；补练后能明确看到新增的回答证据。

**成本 / 依赖**：中；主要是来源关联、有限检查点、复盘与训练接入，复用 V2 的快照和版本机制。[B01、B03、B08、B13、R02、R03、R05、R06]

### 5.2 技术专题题库与自选题单

**为什么值得做**：现在的 `focus` 可以告诉模型重点练什么，但缺少可浏览的专题目录和稳定题目身份。用户不能方便地选“今天练 Redis 持久化这几题”。

**最小流程**：选专题 → 选题 → 盲答 / 模拟 → 复盘 → 接入现有复习与重答。

- 首批只覆盖少量 Java 和 Agent 专题。候选规模可先为 6～8 个专题、每专题 5～8 道审核过的题，数量需要文档评审确认。
- 题目保存稳定 ID、版本、知识点、难度、适用技术版本、题目正文、评分要点和参考来源。自选题单保存顺序和题目版本。
- 默认隐藏答案；浏览答案与盲答分开记录，复用现有“解析已暴露”的比较边界。
- 题目来源可以是本项目原创、明确可使用的公开材料或用户自建题。不是把竞品题库批量搬入本地。
- 不把“阿里 Java”等标签伪装成官方题库或押中概率。需要公司关联时，单独记录可核实的来源和日期。

**建议实现**：小型版本化内容清单与本地题单即可起步；通过独立接入层把选中的题目转换成现有练习输入。现有单题接口主要来自押题或既有练习案例，不能假定它已支持任意题库，需要明确新增契约和兼容测试。

**关键验收**：选定题单与实际主问题一致；题库升级不改变旧尝试的题干和评分标准；不会无声加入题单以外的主题；无答案泄露；题目过期、归档或缺少内容时有明确提示。

**成本 / 依赖**：中；内容维护成本持续存在。先验证首批内容是否有用，再扩大数量。[B01、B03、B04、R02、R04、R06]

### 5.3 简历逐条诊断与保真改写

**为什么值得做**：当前押题能指出风险，JD 诊断能指出证据缺口，故事库能组织经历；但用户还不能从原简历一句话直接走到可确认的修改建议。

**最小流程**：选择简历与目标 JD → 逐条诊断 → 询问缺失事实 → 比较原句与建议 → 单条采纳 → 保存新版本 → 针对新版本押题。

- 分开判断：表达不清、职责不明、证据不足、与岗位关联较弱。不能把关键词没出现直接判成不会，也不能把措辞优化当成能力获得。
- 每条建议带原文、原因、候选改写、资料依据和待补问题。没有量化依据时，建议补充测量过程，不制造百分比和业务规模。
- 用户确认后保存独立版本；旧简历、旧押题和面试快照仍可回看。建议变化不能自动覆盖原始资料。
- 同一底稿可关联不同 JD，但首版只做文本建议和版本，暂不扩展成完整排版与 PDF 模板编辑器。

**建议实现**：复用材料读取、JD 要求、故事中已确认事实和来源快照；新增诊断项、采纳记录和改写版本。复用机制，不把简历硬塞进 STAR 故事的数据含义。提示词和服务端都限制新增事实，关键内容仍需用户确认。

**关键验收**：无依据的数字、职责或结果被拒绝或标待补；单条采纳只修改目标片段；旧版本不变；更换 JD 后明确区分结果；改写中的来源引用可核对；生成失败保留用户手写修改。

**成本 / 依赖**：中；主要难点是事实保真和修改定位。牛客本次初稿将职责与成果扩写，纠正后才收窄，因此验收不能只查是否新增数字，还应覆盖参与范围、完成状态和质量承诺。[B07、B11、B13、R01、R05、R07]

### 5.4 语音口述、转写确认与回放

**为什么值得做**：文字组织得好，未必能够在面试中说清楚。当前四维报告中的表达清晰度是文本判断，不是语速、停顿或口头表现测量。

**最小流程**：录制一段回答 → 停止 → 转写 → 用户确认文本 → 提交现有评估 → 回听音频并重答。

- 首版采用按段录音、按段提交；先解决可回放和转写准确性，暂不追求实时语音对话、插话和数字人。
- 原始音频、原始转写、用户修订文本分开保存。报告明确评的是哪一份文本，不能把用户修订后的流畅程度当成原始口述表现。
- 回放应能对应到本次问题和作答。只有转写确实提供时间信息时才做逐句定位，不生成虚假时间戳。
- 初期先显示真实录音时长；有可靠分段和测量依据后，再做语速与停顿提示。中文字符 / 分钟、英文词 / 分钟分别说明；没有音频证据时不输出这些指标。
- 保留文本作答入口，处理拒绝麦克风、空音频、录制中断、转写失败和重新录制。

**建议实现**：音频保存在本地，绑定尝试 ID 和内容摘要；转写作为独立、显式配置的能力，不假设当前文本模型服务支持音频。文档阶段比较本地转写与远端转写的成本、准确性和资料边界，未经决定不选定外部服务。技术评价复用已有评估链路，口头指标单独展示。

**关键验收**：刷新后已保存音频可回放；失败不丢已录音；编辑文本不覆盖原始转写；Java 类名与 Agent 术语允许人工纠正；口述与修订条件不同的结果不直接给出能力进步分；删除和保留规则可理解。

**成本 / 依赖**：高；需要媒体状态、文件生命周期、转写供应方案和真实音频样本验证。先以固定合成技术回答做小范围试验。[B05、B06、B09、R01、R04、R06]

### 5.5 计时与完整面试轮次

**为什么值得做**：目前“10 分钟”只是规划题量，页面明确“不限时”。用户还不能验证能否在限定时间内讲完开场、技术与项目。

**最小流程**：选训练 / 实战 → 选择有限轮次模板 → 确认时间规则 → 面试 → 按阶段复盘。

- 保留原有不限时训练；实战模板先只提供少数固定阶段：自我介绍、技术、项目、候选人反问。
- 区分总时限、阶段预算、用户实际作答时间和模型等待时间。模型等待、失败恢复、离线和刷新怎样计时必须在规格中写清。
- 例如“10 分钟：开场 1 分钟、技术 3 分钟、项目 4 分钟、反问 2 分钟”只能作为待审核模板，不是当前产品行为。
- 到时处理必须保护草稿：停止继续出题或提示结束的具体策略先审核，不能直接丢弃正在写的回答。
- 报告按实际完成阶段展示，不把未轮到的环节计零分；同一问题的技术质量与回答用时分开反馈。
- 对已出题但主动结束、跳过或到时未提交的情况，明确记录原因和计分规则。快面本次把提前结束时未答的主问题记为 0 分；我们的训练模式应以未作答展示，实战模式如需扣分则在开始前说明。

**建议实现**：服务端保存时间规则、阶段状态和关键时间点，前端负责倒计时显示。不能单靠浏览器定时器决定是否可以提交；先明确时间与当前会话状态机的兼容关系，不改变所有旧会话。

**关键验收**：刷新不重置时限；重复提交不推进两次；模型超时按已定义规则计时；到时草稿可保留；结束与最后一答并发时结果一致；文字与语音如同时支持，时长定义相同。

**成本 / 依赖**：中；计时本身较小，可靠的阶段状态、恢复与边界处理才是主要工作。可以在语音之前单独交付。[B02、B05、B06、R02、R04]

## 6. 暂缓内容与验证顺序

数字人、摄像头表情评分、巨型公司题库、真人匹配、完整在线代码执行和全套简历排版器，均不作为这次首选。它们分别增加媒体、内容运营、协作或运行隔离成本，与当前单人本地训练的最小改进关系较弱。快面的实时面试辅助属于另一种使用场景，本项目继续围绕面试前训练。

建议先完成当前 V2 人工验收，再开展候选文档评审。文档可以并行准备思路，但编码授权应明确到本轮选中的范围。

| 阶段 | 要回答的问题 | 最小验证方式 |
|---|---|---|
| 方案审核 | 这五项是否都做，首批范围多大 | 阅读需求、行为规格、设计和实施计划，逐项决定未决问题 |
| 项目 / 题库小闭环 | 新入口是否真正减少泛练 | 用合成 Java 与 Agent 项目核对缺口归因；选固定题单完成训练并回到复习 |
| 语音小范围试验 | 技术术语转写与回听是否可用 | 固定音频样本核对原文、转写、修订、录制失败和刷新恢复；分别记录失败与成本 |
| 简历与实战 | 修改是否保真，时限是否可靠 | 检查无量化依据的改写、版本回溯、到时草稿及模型等待计时 |

真实模型和音频验证需要固定样本、明确调用预算和停止条件；软件测试通过只能证明对应行为，不能代替质量核对。上表是本项目候选方案的后续验证安排，本轮未执行；第三方实际合成样本及其边界见第 3 节。

## 7. 给 Codex 的文档阶段提示词

### 7.1 提示词诊断

原始要求明确了目标产品、竞品方向和“先写文档、人工审核后编码”的边界。需要补强的主要是当前版本、功能复用和审核出口。

| 原要求中需要明确的事项 | 影响 | 本提示词的处理 |
|---|---|---|
| V2 已实现，但最初仍称“V2 五个功能” | 容易覆盖冻结文档或重复开发 | 将本批标作下一轮候选，不自行命名 V3 |
| “增加项目深挖”等表述过宽 | 容易把已有能力重写 | 要求逐项列明保留、复用和新增，以及本场资料作用域 |
| 登录实测发现改写扩写、未答题计零分 | 容易复制竞品的事实和评价问题 | 增加职责保真、用户纠正、未作答与错误区分的验收 |
| “审核后再编码”缺少可执行出口 | Agent 可能写完文档就直接开发 | 四份文档保持 DRAFT，结束后等待明确批准 |
| 音频与时间规则尚未决定 | 可能提前选外部服务或改变旧会话 | 文档给推荐、代价与待审核决定，禁止实现与付费试验 |

已从仓库取得技术栈、现状和文档职责；无需让用户重复提供。首批专题、转写方案、到时行为等适合在成稿中集中供审核，不阻止先写可审核草案。

### 7.2 推荐组件与工作方式

| 类型 | 选择 | 用途 |
|---|---|---|
| 执行主线 | 当前 Codex 主代理，沿用当前模型 | 单一负责人核对现状、编写四份文档 |
| 工作流 | vibe-workflow 的文档与评审边界 | 使用唯一事实源，不扩大既有批准 |
| 研究参考 | agent-reach、reverse-engineer-anything 的现有结果 | 优先复用证据，区分实见、推断与未知 |
| 提示词 | prompt-optimizer | 固定输入、产物、验收与停止条件 |
| 后续实现 | 另行明确批准后才进入实现和验证 | 本提示词不调用编码、提交或发布流程 |

```text
三、文档职责和路径
先确认地图中是否已有本轮候选文档；有则更新对应唯一入口。
如果没有，使用 docs/vibe/proposals/interview-enhancements/，只创建以下四份草案：
- PROJECT_BRIEF.md：用户问题、目标、最小范围、非目标、优先顺序、成功判断和待决事项。
- SPEC.md：具体行为、数据含义、状态、异常、恢复、用户确认、引用规则及可测试的验收条件。
- TECH_DESIGN.md：模块、页面、接口、数据和迁移建议、模型与音频边界、兼容方案及技术取舍。
- IMPLEMENTATION_PLAN.md：按最小闭环拆分任务、依赖、受影响文件、需求与验收映射、验证方法和停止点。

四、每项必须说明的内容
1. 谁在什么情境使用，当前具体困难是什么；给出一个合成 Java 或 Agent 示例。

3. 完整的最小流程与空态、失败、重试、取消和恢复行为。
4. 数据来源、版本、证据、关联、删除与保留规则；旧会话和旧资料如何继续使用。
5. 可测试的验收条件，标明工程测试、浏览器验证与真实模型 / 音频质量核对的不同职责。
6. 相对复杂度、依赖与风险；不要在缺乏依据时承诺工期或效果。

五、必须正面解决的设计问题
- 项目覆盖中的未问到、未说明、待澄清和有回答证据怎样区分；如何避免把资料不足判错；怎样核对引用和用户纠正。
- 本场使用哪些资料、JD、题单和版本，启动前如何确认并保存；复用现有资料选择与上下文机制，不把现有能力重做。多资料检索是否必要另列取舍，不凭竞品文案认定其后台算法。
- 改写、押题、练习和复盘怎样引用同一资料版本；看过回答思路如何保留提示暴露状态；新资料或 JD 不能无声替换旧结论的依据。
- 题目来源、首批专题规模、内容版本与适用技术版本；题单能否固定实际出题范围；答案暴露怎样影响后续比较。
- 转写采用本地还是远端，资料发送给谁、成本是什么；当前模型接口是否支持音频不能凭猜测。给出建议与替代方案，不配置服务、不发音频。
- 音频、原始转写、用户修订与报告如何关联；刷新、拒绝麦克风、断录、失败和重录怎样处理；没有测量证据时不输出语速和停顿指标。
- 简历修改如何定位原句、单条采纳和回溯；缺少量化依据时怎样询问，不能补造数字；部分参与不能改成独立负责，改进计划不能改成已完成成果，人工核对不能改成准确性保证；JD 匹配不等于实际具备技能。
- 报告怎样区分未作答、主动结束、到时未提交、答错和资料不足；训练模式不把未答写成错误，实战如需扣分要提前说明。评价结论必须定位到实际问答，不能把自述或设想当实现证据。
- 计时由谁决定，模型等待与离线怎样计入；到时怎样保留草稿；结束和回答并发怎样保证一致；旧不限时会话怎样保持兼容。
- 不无条件沿用历史“所有旧源码字节不变”的实施策略，也不擅自废除它；核对其适用范围，对本轮必要改动列出具体兼容建议供审核。
- 数据结构变化只写迁移与备份方案，不执行迁移；模型质量只写样本、预算建议和停止条件，不做真实付费调用。

六、本次边界
不编写业务代码、测试代码或原型，不安装依赖，不改配置或运行中的服务，不访问个人工作资料，不调用付费模型，不提交、推送、部署或创建 PR。
可以核对公开文档，但优先复用已有研究；若补充外部事实，写明来源、日期、实见 / 宣称 / 推断 / 未知。
需要产品决定时，把具体选项、推荐理由和影响写进文档；不把普通内部技术细节反复交给我决定。

七、交付与停止条件
1. 四份文档都能独立阅读，术语、功能编号、需求和验收引用一致，链接可用。
2. 实施计划逐任务对应需求和验收；没有任务在人工批准之前开始编码。
3. 校验文档 diff 和链接，保留用户原有修改；本轮不运行工程测试来假装验证尚不存在的功能。
4. 最终给出文档链接、推荐最小范围、需要我决定的少量关键问题及不确定性。
5. 明确状态：“文档已完成，等待审核，尚未开始编码。”随后结束本轮。
```

### 7.5 这样编写的原因

| 增强 | 作用 |
|---|---|
| 先核对 V2，再确认新增范围 | 避免把旧建议再实现一遍 |
