# 面试产品调研：可借鉴功能与优先建议

调研日期：2026-10-15（北京时间）

适用项目：面试练习室 · AI 技术面试助手

项目比较基线：V1，代码提交 `20fc7cfa51d7983a4ad766e14380d3437b4f5e8b`

文档性质：竞品调研与候选建议，尚未成为批准的需求、架构决定或开发授权。

阅读建议：先看第 1 节的优先建议，再用第 3 节核对我们已有的能力、第 5 节比较候选功能。需要核查依据时，阅读第 6 节的前端文件分析和第 9 节的来源。

本报告保留调研时的 F1～F8 建议。后续 [V2 范围草案](../vibe/releases/v2/PROJECT_BRIEF.md) 只选了 F1～F5，并进一步缩小范围；例如分阶段设计训练不跳过阶段，也不包含组件连线数据。V2 仍待审核，不能把本报告的全部建议当作实施范围。

## 1. 最值得优先解决的问题

**建议先帮助用户反复练习真实薄弱点，并用新旧回答检查问题是否得到修正。**

我们已经具备简历押题、项目深挖、动态追问、资料依据、逐题复盘和薄弱项专项练习。相比继续增加出题入口，我更建议优先解决以下三个问题：

1. 我反复不会的到底是什么，今天应该优先练什么？
2. 按建议修改之后，我的回答是否确实更好了？
3. 对当前目标岗位，还有哪些能力没有被有效验证？

据此，本报告推荐的前两项核心能力是：

- **错题复习与能力档案**：从报告中提取可追踪的薄弱技能，关联原题、原回答和证据，形成复习队列。
- **同题二答与进步对照**：固定题目、资料上下文和评分标准，保留每次真实回答，验证问题是否得到修正。

岗位差距诊断、行为面试故事库和阶段式系统设计训练是后续候选；语音、可执行编程环境、真人互面涉及更大的工程或运营成本，应分别评估。这里的排序是结合本项目定位作出的产品判断，并非竞品市场份额排序或已经验证的需求强度。

## 2. 调研了什么，证据能说明什么

### 2.1 样本选择

选择 9 个具有代表性的产品，覆盖国内技术题库、算法练习、技术模拟面试、表达训练和综合求职训练。这里的“主流”指常见的代表性产品类型，**没有取得可比较的活跃用户或收入数据，不作市场排名**。

| 产品 | 主要类别 | 本次重点观察 |
|---|---|---|
| 牛客 | 国内求职、题库、面经与模拟面试 | 公司及岗位题单、面试场景覆盖 |
| 面试鸭 | 中文技术面试题库与练习 | 刷题路线、掌握状态、题目练习入口 |
| LeetCode / 力扣 | 编程练习与面试准备 | 学习计划、公司题目、限时测评 |
| Hello Interview | 技术面试内容与训练 | 系统设计分步练习、白板、行为及 AI Coding |
| Aced，原 Exponent，含原 Pramp 互面能力 | 技术课程、互面与 AI 训练 | 真人互面、评分规则、公司面试流程 |
| interviewing.io | 技术模拟面试与辅导 | 真人反馈、AI 技术面试、代码和音频协作 |
| Yoodli | 口头表达与情景训练 | 动态追问、表达分析、录制回看 |
| Big Interview | 综合面试训练 | 回答构建器、故事素材沉淀、视频练习 |
| Huru | 岗位定制与录制式面试训练 | JD 导入、逐答反馈、重复作答、进步趋势 |

### 2.2 方法与限制

公开资料通过 agent-reach 的 Exa 搜索、Jina Reader、B 站搜索 API 和 V2EX 公开 API 获取。另使用 reverse-engineer-anything 提供的 REA 命令行工具（CLI），检查两个网站公开发布的 JavaScript 文件；这一过程只读文件，不运行其中代码，称为静态分析。项目现状则直接核对仓库文档、页面、接口、提示词和数据库定义。

本报告中的 JD 是岗位描述，Agent 指能调用工具并管理任务状态的 AI 应用。F 编号对应候选功能，S 对应官方来源，C 对应社区来源，R 对应仓库依据，E 对应静态分析证据。具体来源见第 9 节。

不同证据能支持的结论如下：

| 标记 | 含义 | 能支持的结论 |
|---|---|---|
| 官方说明 | 当前官网、帮助文档或官方页面 | 厂商公开描述的功能；不代表本次完成体验验收 |
| 公开页面观察 | 本次实际取得的匿名访问页面文本 | 页面确实展示的入口、信息或登录边界 |
| 静态观察 | 公开发布脚本及 REA 分析 | 当前产物中存在的配置、代码分支和请求封装 |
| 实现推断 / 建议 | 基于证据与本项目代码形成的设计 | 可供我们实现的方案；不代表竞品后台事实 |
| 未知 | 登录、付费、动态加载或服务端不可见部分 | 不填补为“已实现”，也不推断为“没有” |

本次未注册新账号、购买服务、提交个人简历或执行第三方写接口；没有测量各产品的真实模型质量、真实延迟或录用效果。检索文章中的成功率和厂商宣传数字未作为推荐依据。

Exa 部分查询触发免费限流，后续以可访问的官方页面补充。Reddit、小红书、Twitter 未取得可用后端，因此没有冒充覆盖这些平台。B 站结果包含旧视频、机构推广与资料引流，只辅助定位中文场景，不作为独立用户口碑。V2EX 仅抽取两篇主题及其回复中的具体反馈，样本不足以代表用户总体。

## 3. 我们已经有什么，还缺什么

以下“未具备”限定于上述提交的 V1 代码、公开契约和页面，不根据界面宣传语推断能力。

| 能力 | 当前状态 | 核对依据 | 差距的准确表述 |
|---|---|---|---|
| 岗位、级别、JD 定制提问 | 已有 | 配置页、`InterviewService` 的 `jd` / `focus` 输入、规划提示词 | 缺少结构化的 JD 能力要求与证据覆盖诊断；不是缺少 JD 输入 |
| 简历押题与单题练习 | 已有 | 押题接口和 `PredictionQuestion` | 缺少跨练习的掌握状态、题目复习队列 |
| 项目整体理解、实现深挖、场景权衡 | 已有 | V1 REQ03、规划和面试官提示词 | 缺少逐阶段设计产物、架构图和阶段反馈；不是缺少深度追问 |
| 回答驱动的追问 | 已有 | 每道主问题最多两次追问，后端控制切题 | 不应把“动态追问”再次包装成新增核心功能 |
| 逐题反馈、回答思路与知识解释 | 已有 | `Report`、评估提示词、报告页 | 缺少固定评分标准下的多次回答对照 |
| 薄弱项专项练习 | **已有部分流程** | `Report.vue:43` 把薄弱项、岗位和级别传到 `/configure/quick`；规划优先覆盖 `focus` | 缺少稳定技能 ID、来源关系、复习时间和后续改善验证 |
| 历史对话与报告 | 已有 | 历史页、会话和报告持久化 | 缺少跨场技能趋势；当前主要按场次回看 |
| 自我介绍、行为面试故事库 | 无专用结构 | 模式仅 `QUICK / RESUME / PROJECT`；没有故事、版本和复用关系 | 自定义岗位文本可能问到相关内容，但不等于具有故事管理能力 |
| 语音表达与回放 | 未具备 | 会话消息只有文本，无音频资源和时间轴 | 无法训练语速、停顿、口头组织及录音回看 |
| 可执行编程、SQL、代码诊断 | 未具备 | 无编辑器、执行接口、测试结果模型 | 文本讨论代码不等于真实运行验证 |

当前数据库只有资料、文档、会话、押题和报告五类业务表，没有技能观察、复习队列、作答版本、故事卡片或代码运行记录。[R1–R7]

**应保留的已有优势**：原始回答与模型点评分开保存；“答错”“遗漏”“资料不足”分开表达；资料引用受服务端校验；面试期间不主动泄露答案。这些都应成为后续训练能力的基础。[R2、R4、R6]

## 5. 候选核心功能与优先顺序

P0 表示建议优先做，P1 表示随后评估，P2 表示暂缓或单独试验。这些只是调研建议，不改变 V1 范围。

复杂度为相对估计：“中”表示需要同时修改前后端和数据结构；“高”表示还涉及媒体、代码隔离执行或较大交互系统。这里没有工期承诺。

| 编号 | 候选能力 | 当前差距 | 建议 | 复杂度 | 推荐理由 |
|---|---|---|---|---|---|
| F1 | 错题复习、稳定技能标签与能力档案 | 已有单场薄弱项，无长期状态 | P0 | 中 | 最贴近现有报告，能回答下一次该练什么 |
| F2 | 同题二答、答案版本与改进对照 | 有历史，无专门的可比较尝试关系 | P0 | 中 | 能检查反馈是否被落实，与 F1 组成从复习到检查改进的完整流程 |
| F3 | JD 差距诊断与短冲刺清单 | 已有 JD 定制，无证据覆盖表 | P1 | 中 | 让岗位相关性可见，减少泛练 |
| F4 | 自我介绍与 STAR 故事库 | 无专用故事及版本模型 | P1 | 中 | 把项目经历转化为真实、可复用的面试表达素材 |
| F5 | 阶段式系统设计与 Agent 架构训练 | 有项目追问，无阶段产物 | P1 | 中到高 | 与 Java 后端、Agent 岗位定位匹配，具有技术训练辨识度 |
| F6 | 语音作答、逐句回放与表达反馈 | 仅文本 | P2，先小范围试验 | 高 | 可补齐口头表达，但应先解决转写准确性和交互稳定性 |
| F7 | 代码诊断、SQL 或 AI 协作实操 | 无执行验证 | P2，独立探索 | 高 | 验证动手能力；完整在线评测不宜直接塞入现有本地服务 |
| F8 | 公司 / 轮次训练模板与精选题单 | 已有岗位，无专用公司流程内容 | P2，内容先行 | 中，长期内容成本较高 | 借鉴组织方式，避免先承担持续抓取与题库维护 |

### 5.1 F1：错题复习与能力档案

**用户结果**：打开产品后，看到今天应该复习的几项真实薄弱点；能够回到首次失误及后续修正证据。

最小流程：报告产生薄弱点 → 确认技能标签 → 进入复习队列 → 盲答原题或等价变式 → 保存新观察 → 更新状态与下次复习时间。

我们可借鉴面试鸭的轻量标记方式，但需要补上“模型评估”和“用户自评”的区别。用户点击已掌握，只能形成自评；不能直接覆盖有证据的历史错误。Huru 的跨次趋势和力扣的学习进度提供了产品参考，但不表明它们采用同一种内部算法。[S03–S05、S17、E1、E2]

**建议实现**：

- 复用 `Report.questions`、`weaknesses`、原始消息、`focus` 入口及 SQLite。
- 增加稳定的 `skillId`，先维护小规模 Java / Agent 技能词表；模型只能选择已知 ID，另设待确认标签。不要依靠每次自由生成的中文短语直接归类合并。
- 新增观察时保留旧记录，用 `skillObservation` 保存 `sessionId`、`questionIndex`、`skillId`、问题类型、回答证据、评分规则版本和来源。
- 将 `selfRating`、`evaluationStatus` 与 `reviewStatus` 分开。资料不足仍为未知，不能按答错安排惩罚性复习。
- 复习队列保存来源题、最近尝试、状态与 `nextReviewAt`；先按明确规则排序。用户进入页面时查询到期项即可，暂不需要常驻调度或通知系统。
- 导入旧报告时建立一次性观察记录，按来源与版本去重；报告重试生成不能不断制造新错题。

**建议验收**：重复生成同一报告不增加重复项；同义技能能够归并；未知项不变成错题；复习完成后仍可回看原错误；用户能够纠正模型误判。复习间隔策略需通过真实使用校准，本次不宣称任何算法已被证明最适合该产品。

### 5.2 F2：同题二答与进步对照

**用户结果**：同一道题第一次说不清，按反馈修改后再答，明确看到补足了哪些证据、仍遗漏什么。

最小流程：报告页选择重答 → 隐藏参考答案 → 重新提交 → 按原评分规则评估 → 展示两次原文、已修正项、新问题和下一步。可增加显式教练提示，但必须与盲答结果分开。

Huru 公开强调同一套标准下的重复作答；Big Interview 支持回答保存、修改与再次练习。我们可在现有逐题报告上实现更窄的技术版。[S15、S17]

**建议实现**：

- 新建独立 `practiceAttempt`，关联来源会话和题号；不编辑原 `Session.messages`，保持历史真实性。
- 固定题目版本、资料快照、`rubricVersion`、模型及关键参数；记录是否已展示答案、是否使用提示。
- 对“错误已经修正”“新增证据”“仍然遗漏”分别给出原文依据。两次分数的变化只是辅助信号。
- 同模型、同规则仍可能有评分波动；更换模型或规则后标记不可直接比较，避免把模型变化绘制成能力提升。
- 先实现单题重答和对照，再考虑完整教练对话，控制交互复杂度。

**建议验收**：原回答不可被新版本覆盖；同一尝试重试不重复记分；评分变化可追溯；使用提示的尝试有明确标记；至少对一组人工审阅的“无改进 / 局部改进 / 明显改进”合成回答做校准，并另留真实模型验证记录。

### 5.3 F3：JD 差距诊断与短冲刺清单

**用户结果**：输入一个目标岗位，看到要求、现有经历证据、已验证能力、待验证能力和下一项练习。

差异不在重新生成一份 JD 题单，而在形成下面的可核查映射：

| JD 要求示例 | 经历证据 | 训练证据 | 建议动作 |
|---|---|---|---|
| 熟悉缓存一致性 | 项目材料提及 Redis，但未说明一致性策略 | 已练过期与淘汰，尚未验证更新竞争 | 安排一道更新竞争场景题 |
| 能评估 RAG 质量 | 简历写到检索增强 | 没有评测集和指标相关回答 | 先追问真实实践，再决定补学或补充资料 |

表格是本报告的合成示例，不来自竞品数据。Huru 的 JD 定制与覆盖展示、Aced 的公司面试流程、力扣的专题准备提供了组织方式上的参考。[S05、S09、S17]

**建议实现**：JD 要求结构化 → 关联材料短引 → 关联 F1 技能观察 → 区分已验证、待验证、证据不足 → 用户选择有限数量的下一步练习。复用已有 JD 资料和规划接口，不自动联网抓职位，不先生成复杂日历。

**建议验收**：JD 中没有的要求不能冒充必需项；简历关键词不能自动判定已经掌握；一条训练证据不能覆盖整个大技能；所有诊断能回到原文。早期不展示虚假的“录用概率”或精确就绪率。

### 5.4 F4：自我介绍与行为面试故事库

**用户结果**：把一次真实故障处理、合作冲突或技术决策整理成故事，针对不同问题调整表达，并保持事实一致。

Big Interview 的回答构建器提供了可直接参考的组织方式；STAR 表示情境、任务、行动、结果。结构本身只是引导，不能替代真实个人贡献。[S15]

**建议实现**：在项目资料旁增加候选故事卡，记录背景、个人行动、结果、学习、来源短引、适用能力及版本；提供自我介绍和行为问题两个初始模板。复用文本编辑、资料快照、单题训练和 F2 作答版本机制。

对没有写清的指标显示“待补充”，由用户提供事实；禁止自动补写百分比、规模或职责。故事与来源材料关联，但面试引用保存当时快照。先验证“项目介绍”“失败与复盘”“技术分歧”几个与当前用户相关的场景，再扩展 HR 题型。

**建议验收**：不同版本不引入互相矛盾的职责或数字；个人行动与团队成果明确区分；同一故事可适配多个问题但不会被机械照搬；缺少经历时提示补充，不能编造。

### 5.5 F5：阶段式系统设计与 Agent 架构训练

**用户结果**：完成一个设计问题时，持续产出需求、接口、架构和权衡，而不只是回答面试官随机提出的知识题。

Hello Interview 的公开流程对这一方向最有启发。其官方介绍提供了分步设计与反馈的功能证据，但没有向本次调研开放服务端实现。[S07、E3]

**建议实现**：

1. 设置明确阶段：需求澄清 → 约束和容量 → 实体与 API → 架构 → 故障及权衡。根据题目允许跳过不相关阶段。
2. 每个阶段保存用户产物、依据、未解决问题和反馈，后端控制阶段推进。可复用会话恢复和幂等设计，不能只让模型自由输出阶段名。
3. 第一版先用分区文本与结构化组件、连线数据；图形白板另作范围。采用什么绘图库属于后续技术选型，本次没有证明 Hello Interview 实际使用某个编辑器。
4. 评分按阶段标准和题目约束判断。设计存在多种合理答案，不能把与参考图不同直接判错。

针对 Agent 岗位，可用合成案例训练检索质量、工具失败、权限约束、状态恢复、成本与延迟等权衡；这属于结合本项目定位提出的扩展，未声称是某家竞品的完整训练内容。

**建议验收**：阶段产物刷新后保留；反馈引用真实产物；缺少约束时先澄清；替代架构可以获得合理评价；无依据的容量数字标为假设。文本阶段有效后，再验证图形输入是否带来足够收益。

### 5.6 F6：语音作答、回放与表达反馈

**用户结果**：真正开口完成技术说明，回放自己停顿、重复和表达不清的部分；技术内容与口头表现分别反馈。

Yoodli 和 Huru 提供了明确的公开功能参考。Yoodli 帮助文档还提供关闭自动回应、改用手动下一次回应的方式，可作为处理误打断的交互参考。[S12–S14、S17]

**建议最小方案**：录音 → 独立转写适配层 → 用户确认文本 → 复用当前提交回答与追问链路；音频单独保存，通过消息关联回放。先采用按键或明确操作结束回答，再考虑全双工实时对话与自动断句。

语速、停顿等指标依赖音频及时间信息；不能从修改后的文本反推出真实口头表现。转写修订版应与原始转写分开。中文技术词、英文标识符和口音需要单独验证，不照搬英文语速阈值。当前文本模型接口能否提供转写或语音能力未知，需要独立确认服务、费用和外部数据流。

**建议验收**：拒绝麦克风后有明确可用路径；误识别可以修订；转写重试不会重复发送答案；录制、转写、提交、等待、失败状态明确；反馈能够定位原音频。先做可用性及转写准确性小样本验证，再决定实时化。

### 5.7 F7 / F8：值得保留，但单独评估

**代码与 AI 协作实操**：LeetCode、interviewing.io 和 Hello Interview 分别提供执行评测、技术模拟及 AI Coding 训练参考。[S04、S06–S08、S11] 对我们更合适的起点可能是短代码解释、故障归因、SQL 分析、检查一份 AI 生成代码的缺陷。若要宣称运行正确，必须有确定性的测试结果；模型点评不能代替执行。未来若开放任意代码运行，需要独立隔离执行、资源限额与文件网络边界，不能在持有模型密钥的应用进程中直接运行。

**公司与轮次模板**：先允许用户手工选择或维护经过审阅的训练模板，记录来源日期与适用岗位。公司题目属于历史样本，不宣称“本次必考”。牛客和 Aced 的组织方式可借鉴，但持续联网抓面经涉及内容质量、重复、时效和使用边界，属于独立范围。[S01、S09]

### 6.2 面试鸭：前端怎样处理题目标记

**静态观察，高置信度**：[E1、E2]


### 7.1 分三步判断是否值得继续

| 步骤 | 候选范围 | 需要回答的问题 | 验证方式 |
|---|---|---|---|
| 第一步 | F1 + F2 的最小可用流程 | 用户是否因此回到真实薄弱点并修正回答？ | 观察有证据的重答、人工检查改进、记录误判与重复项；软件流程与真实模型质量分开验证 |
| 第二步 | F3；再从 F4 / F5 中选一个 | 岗位聚焦、故事表达或系统设计，哪项最符合实际准备任务？ | 用同一批目标岗位与合成资料完成端到端体验，记录无关提问和证据不足项 |
| 第三步 | F6 或 F7 的独立小试验 | 开口练习或动手实操带来的增益，是否足以覆盖新成本？ | 分别测转写修订、可用性，或确定性执行结果；验证通过再扩大范围 |

### 7.2 优先验证的指标

- 报告之后产生真实重答的比例，而不是只统计“点击专项练习”。
- 同一薄弱点在后续原始回答中被修正的比例，抽样人工核对。
- 需要用户纠正的模型误判、错误归类和重复技能比例。
- 从看到问题到完成一次有效重练需要的步骤与等待成本。
- 同一组回答在固定模型、固定规则下的评分稳定性。

这些是建议的评估方法，尚未采集数据，也没有预先声称新增功能能够提升留存或录用率。

### 7.3 暂缓的方向

| 方向 | 暂缓理由 | 可保留的较小做法 |
|---|---|---|
| 万题题库与全网面经聚合 | 内容维护和时效是长期工作，与现有个性化训练不完全同向 | 自有少量审阅题与用户主动导入 |
| 真人互面、导师预约和社区 | 需要多人平台、供给、匹配和运营，明显超出本地单人定位 | 以后考虑导出材料供人工反馈 |
| 实时面试代答或隐蔽提示 | 训练目标无法用是否提示成功来衡量，且改变现有正式面试规则 | 在明确练习阶段提供教练提示 |
| 数字人外观和复杂人格矩阵 | 暂无证据表明优先级高于训练效果和状态稳定性 | 先保留当前常规 / 压力风格 |
| 精确录用概率、跨用户排名 | 没有足够的标注、样本和可比评分条件 | 展示有依据的个人变化与未知项 |
| 为以上功能先引入向量库、消息队列或 Multi-Agent 框架 | 当前已知最小方案尚不需要这些依赖 | 先沿用普通服务编排与 SQLite，按真实瓶颈再判断 |
